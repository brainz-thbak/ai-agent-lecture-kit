# 구현·회귀 검증

## 검증 입력 확인

1. **호출자가 실제 요구사항 파일을 전달한 경우에만 검증을 시작한다.** 명시된 경로나 첨부에서 확보한 실제 파일을 사용한다. 작업 ID나 요구사항 원문이 대화에만 있으면 파일을 요청하고 `BLOCKED`를 반환한다.
2. [요구사항 파일 형식](references/requirements-file.md)에 따라 스킬 폴더의 `scripts/read-requirements.mjs`를 Node.js로 실행해 실제 파일에서 작업 ID와 본문을 읽는다. 파일을 읽을 수 없거나 ID가 비어 있거나 중복되면 테스트를 실행하지 않고 `BLOCKED`를 반환한다. 호출자가 별도로 지정한 ID가 있으면 파일의 ID와 일치하는지 확인한다.
3. 파일에 담긴 작업 ID와 실제 파일 경로를 검증 응답에 사용한다. 요구사항과 함께 전달된 확정 테스트 케이스를 읽고, 케이스에 작업 ID가 있으면 같은 작업인지 확인한다. 문서나 케이스의 대상이 서로 다르면 그 차이를 보고하고 올바른 입력을 요청한다.

## 검증 범위 정하기

1. 요구사항 파일의 각 필수 수용 기준과 전달받은 중요 회귀 기준을 테스트 케이스에 연결한다. 확정 케이스가 있으면 기대 결과와 필수 여부를 그대로 사용한다. 별도 케이스가 없는 경우에는 파일에 확정된 기대 결과를 기준으로 재현 절차를 작성하고, 기존 동작을 확인할 경로와 근거를 연결한다.
2. 관련 기준의 기대 결과가 미결이거나 충돌하면 요청자에게 확인한다. 필요한 케이스, 자료 또는 환경을 확보할 수 없으면 해당 범위를 미검증으로 남긴다.

## 실행하고 증거 남기기

1. 검증 대상을 특정한 뒤 API, 화면, CLI 등 실제 이용 경로에서 필수 신규 동작과 회귀를 모두 실행한다. 격리된 테스트 데이터로 상태 변경을 검증한다. 시간과 경계값에 의존하는 케이스는 판정에 사용한 기준 시각과 사전 조건을 기록한다.
2. 케이스마다 실행 절차, 기대값, 실제값과 관찰 근거를 남긴다. `PASS`는 관찰값이 기대값과 일치할 때만 사용한다. `FAIL`은 유효한 케이스에서 구현 결함을 재현했을 때만 사용한다. 테스트 오류, 실행 장애, 미확정 기대값으로 판정할 수 없는 케이스는 `UNVERIFIED`로 기록하고 이유를 `issues`에 남긴다.
3. 제품 코드, 요구사항 및 확정 케이스는 검증 중 그대로 둔다. 수정 후 재검증할 때는 같은 요구사항 파일과 확정 케이스로 실패 사례뿐 아니라 필수 신규 동작과 회귀를 모두 다시 확인한다.

## 결과 반환

아래 순서대로 판정하고 해당하는 첫 상태를 반환한다.

- `FAIL` — 재현된 구현 결함이 있다. 실패한 케이스 ID, 실행 절차, 기대값, 실제값을 함께 반환한다.
- `PASS` — 필수 수용 기준과 회귀 범위가 케이스에 연결되어 있고, 필수 케이스를 모두 실제로 실행해 통과했다.
- `BLOCKED` — 입력이 유효하지 않거나, 확인된 구현 결함 없이 필수 범위를 판정할 증거가 부족하다. 필요한 입력, 결정 또는 재실행 조건을 반환한다.

[응답 스키마](references/response.schema.json)에 맞춰 최종 응답을 단일 JSON 객체로 작성한다. 확인한 파일이나 ID가 없으면 해당 값은 `null`로 둔다. 케이스 ID를 중복 없이 사용하고, 각 이슈에 영향을 받는 기준이나 케이스 ID와 다음 행동을 적는다.
