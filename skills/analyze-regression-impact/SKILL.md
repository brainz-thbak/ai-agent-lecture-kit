# 회귀 영향 분석

## 분석 범위 정하기

1. 변경 요청에서 바꾸려는 동작과 유지해야 할 기존 동작을 구분한다. 수용 기준 ID가 제공되면 그대로 사용한다. 자연어 요청만 있으면 명시된 기대 동작에 `AC-01` 형식의 분석용 ID를 붙인다. 기대 동작의 의미가 불명확하면 그 자체를 분석 결과에 남긴다.
2. 판단에 필요한 문서와 기존 관찰 결과를 읽고 코드 조사 범위를 정한다. 확인한 경로와 자료를 `scope.reviewed_sources`에, 확인 범위의 한계를 `scope.limitations`에 적는다.

## 코드 조사 위임하기

코드에 접근할 수 있으면 [코드 분석 서브에이전트 지침](references/code-analyzer.md)을 읽고 서브에이전트 도구로 코드 조사 전담 에이전트 한 명을 실행한다. 작업공간과 대상 경로, 변경 의도, 관련 수용 기준, 확인할 질문을 전달한다. 기존 판단이 있다면 확인된 사실만 입력으로 전달한다.

서브에이전트의 응답을 받은 뒤 판정에 영향을 주는 코드 근거를 직접 확인한다. 근거가 부족하면 먼저 같은 에이전트에 확인할 경로나 질문을 좁혀 전달한다. 서브에이전트 도구를 사용할 수 없으면 접근 가능한 코드를 직접 조사하고, 그 사실을 `scope.limitations`에 적는다. 코드나 필수 근거를 확보하지 못하면 판정 규칙에 따라 처리한다.

코드 조사 결과를 바탕으로 후보를 작성하고, 최종 판정과 JSON 응답은 이 스킬을 실행한 에이전트가 작성한다.

## 회귀 후보 정리하기

1. 조사 결과를 수용 기준별로 연결한다. 변경을 일으키는 진입점, 데이터 변경이나 외부 호출, 그 결과를 읽거나 같은 자원을 쓰는 호출자 사이의 연결을 확인한다. 권한, 경계값, 기존 데이터 형식, 실패와 재실행에 미치는 영향은 변경과 관련 있는 경우에 검토한다.
2. 각 후보에 `REG-01` 형식의 ID를 붙인다. **어떤 변경이 어떤 경로를 통해 어떤 기존 동작을 깨뜨릴 수 있는지** 적는다. 같은 원인과 기대 결과를 공유하는 후보는 합치고, 관련된 기준 ID를 모두 연결한다.
3. 현재 동작과 그 근거를 남긴다. 코드와 문서에서 추론한 위험은 `POTENTIAL`로 표시한다. 문제를 직접 재현한 경우에만 `REPRODUCED`를 사용하고, 실행 절차와 관찰 결과를 근거에 포함한다. 일부 동작을 모의 실행했다면 실제로 확인한 문제와 모의 실행 조건을 함께 적는다.
4. 기존 동작을 확인할 방법을 사전 조건, 실행할 동작, 관찰 가능한 기대 결과로 작성한다. 데이터 손실, 접근 권한 위반, 외부 계약이나 주요 사용자 동작의 파손처럼 변경을 막을 만한 영향은 `REQUIRED`로 표시한다. 그 밖에 검증할 가치가 있는 영향은 `OPTIONAL`로 표시한다.
5. `coverage`에 각 수용 기준에서 살핀 경로와 영향 경로를 확인한 결과를 남긴다.
   - `CANDIDATES_IDENTIFIED` — 영향 경로를 찾았다. 검증의 기대값이 미결이어도 경로를 파악했다면 이 상태를 사용한다.
   - `NO_CANDIDATE_IDENTIFIED` — 접근 가능한 관련 경로를 검토했고 회귀 후보를 찾지 못했다.
   - `UNDETERMINED` — 정보가 부족해서 관련 경로를 충분히 분석할 수 없다. 확인한 후보가 있으면 그 ID와 부족한 근거를 함께 남긴다.

## 판정하기

아래 순서로 확인하고 해당하는 첫 상태를 반환한다.

- `BLOCKED` — 요청자 결정이나 핵심 증거가 없어서 기대 동작이나 중요 영향을 판단할 수 없다. `issues`에 필요한 결정이나 자료, 관련 ID와 다음 행동을 적는다. 제품 동작에 관한 결정을 임의로 확정하지 않는다. 요청자에게 어떤 선택을 확인해야 하며 결과가 어떻게 달라지는지 적는다.
- `REVISE` — 확인한 근거로 수정 방향을 제시할 수 있지만, 요구사항에 누락, 충돌 또는 관찰하기 어려운 수용 기준이 있다. `issues`에 해당 기준과 구체적인 보완점을 적는다.
- `PASS` — 검토 범위에서 수용 기준별 분석이 끝났고, 반환할 후보마다 근거와 재현 가능한 확인 방법이 있다. 이 판정은 분석의 충족 여부를 나타낸다.

## JSON 반환

[응답 스키마](references/response.schema.json)를 읽고 그 형식에 맞는 JSON 객체 하나를 반환한다. 필요하면 [응답 예시](references/response-example.json)에서 미결 정책을 기록하는 방법을 확인한다.

최종 JSON에서 기준, 후보, 이슈의 ID는 각각 중복 없이 사용한다. 후보와 기준의 연결이 양방향으로 일치하고, 이슈가 가리키는 ID가 응답에 있는지 확인한다. 분석할 수 없었던 기준은 `UNDETERMINED`로 표시하고 이유를 적는다. 기대값을 확정할 수 없는 후보의 `verification`은 `null`로 두고 해당 후보를 `issues`의 `related_ids`에 연결한다. 해결할 항목이 없으면 `issues`는 빈 배열로 반환한다.
