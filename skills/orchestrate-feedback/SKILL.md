# 구현 피드백 루프

## 순서도에 따라 실행

1. [순서도와 전이 조건](references/workflow.md)을 읽고 `refine`에서 시작한다. 현재 노드 ID, 작업 ID, 요구사항 파일 경로, 확정 케이스와 현재 유효한 판정을 작업 컨텍스트에 유지한다.
2. 현재 노드의 작업을 수행하고 실제 산출물이나 응답을 확인한다. 해당 노드의 전이 조건이 충족되면 순서도에 연결된 화살표를 따라간다. 서브에이전트가 응답하기 전에는 현재 노드에서 대기한다.
3. 판정 응답의 형식과 대상부터 확인한다. 이전 요구사항을 기준으로 받은 분석이나, 다른 작업 또는 수정 전 코드에 대한 검증 결과를 다음 단계의 근거로 사용하지 않는다. 해당 노드에서 유효한 응답을 확보한다.
4. 완료는 `verificationGate`의 유효한 `PASS`를 받아 `done`에 도달했을 때 선언한다. `incomplete`에 도달하면 아직 끝나지 않은 항목과 진행을 막는 이유를 보고한다.

## 구현 전

- **`refine`** — [요구사항 구체화 스킬](../refine-requirements/SKILL.md)로 상세 요구사항을 실제 Markdown 파일에 저장한다. 문서 맨 위에 요청에서 지정한 `task_id`를 쓰거나 이번 작업에 사용할 고유 ID를 생성해 쓴다. 경로가 지정되지 않았으면 작업용 임시 디렉터리에 저장한다. 요구사항을 갱신해도 파일과 작업 ID를 유지한다.
- **`analyze`** — 현재 요구사항 파일과 관련 코드 경로로 [회귀 영향 분석 스킬](../analyze-regression-impact/SKILL.md)을 직접 실행한다. 이 스킬에서 코드 분석 서브에이전트를 호출하고 최종 JSON을 작성한다.
- **`revise` / `clarify`** — `revise`에서는 분석의 보완점을 요구사항 구체화에 전달한다. `clarify`에서는 필요한 결정을 요청자에게 확인하거나 필요한 자료를 확보한다. 이후 갱신된 요구사항 파일을 다시 분석한다.
- **`cases`** — 신규 동작 및 회귀 테스트 케이스를 작성한다. 각 수용 기준과 중요한 회귀 후보를 필수 케이스에 하나 이상 연결한다. 각 케이스에 ID, 관련 기준, 필수 여부, 사전 조건, 실행 절차, 기대 결과를 적고 상태를 `UNVERIFIED`로 둔다. 케이스와 기대 결과를 확정한다.

## 구현과 검증

- **`implement`** — **첫 구현과 수정은 반드시 구현 서브에이전트에 위임한다.** 첫 구현에는 구현자 한 명을 실행하고, 재작업은 기존 구현자에게 이어서 맡긴다. 작업 ID, 실제 요구사항 파일 경로, 확정 테스트 케이스, 작업공간과 수정 범위를 전달한다. 구현자는 제품 코드만 수정하며 요구사항과 테스트 케이스의 수정 및 테스트 실행은 금지한다. 변경 파일, 변경 내용, 남은 문제를 돌려받고 요구사항 파일과 확정 케이스가 그대로인지 확인한다.
- **`verify`** — 별도의 검증 서브에이전트를 실행한다. [구현·회귀 검증 스킬](../verify-implementation/SKILL.md)에 실제 요구사항 파일 경로, 확정 케이스, 현재 변경 범위를 전달한다. 첫 검증과 재검증 모두 확정된 신규 동작 및 회귀 케이스를 실행한다.
- **`feedback`** — 실패한 케이스 ID, 재현 절차, 기대값, 실제값을 기존 구현자에게 위임할 입력으로 정리한다. 새 근거 없이 같은 실패가 반복되면 미해결 항목과 근거를 정리한다.
- **`resolve`** — 누락된 입력, 테스트 또는 실행 환경 문제를 해결한다. 기대 동작에 새 결정이 필요하면 요청자에게 확인하고 요구사항부터 다시 진행한다.
